Você desliga o sorteio e manda o modelo escolher sempre o token de maior pontuação. Parece suficiente para repetir a resposta. Mas a escolha é só uma parte do caminho: antes dela, alguém calculou as pontuações.

O [estudo da Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) mostrou que mudar o agrupamento de requisições pode afetar esse cálculo. Isso não significa que toda execução vai divergir, nem que duas respostas diferentes revelem sozinhas a causa. Vamos começar separando as duas coisas.

<Aposta dados={previsoes} pergunta="Antes de construir: o que uma escolha fixa e uma resposta repetida permitem afirmar?" />

## O que vamos construir

Um instrumento pequeno para comparar respostas. Primeiro, uma soma em que o arredondamento aparece. Depois, um seletor que escolhe sempre o maior valor. Por fim, um medidor aplicado a um modelo real: ele guarda os tokens, encontra o primeiro ponto diferente e conta quantas execuções coincidem.

<MapaTemperatura />

A temperatura atua na escolha, depois do cálculo. No modo guloso, a alternativa de maior valor vence sem sorteio. Isso não fixa os valores produzidos antes: bibliotecas podem organizar as contas de formas diferentes. O [PyTorch documenta essa diferença entre cálculo isolado e em lote](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html#batched-computations-or-slice-computations).

<PareEPense pergunta="Se as pontuações mudarem um pouco, o próximo token precisa mudar?">
Não. Uma alternativa que vence com folga pode continuar vencendo. Vamos construir uma troca de ordem que inverte a escolha e depois aumentar a margem para ela deixar de inverter.
</PareEPense>

## Uma prova de cada vez

Na primeira parte, cada soma intermediária é arredondada para binary16, um formato de 16 bits. As entradas são as mesmas; os parênteses mudam quando ocorre o arredondamento. Um teste que pressupõe que as duas contas sempre dão o mesmo falha de verdade.

Essa prova tem um limite: não executa um LLM e não mede uma GPU. Muitas operações reais acumulam em outra precisão. Para aprender o mecanismo, escolhemos valores que revelam o arredondamento; para medir um modelo, precisamos de outra coleta.

<PareEPense pergunta="Se você repetir mil vezes a mesma soma, com os mesmos parênteses, o arredondamento precisa produzir mil resultados diferentes?">
Não. A ordem fixa pode repetir exatamente. Sensibilidade à ordem e variação entre execuções são coisas diferentes; o nosso controle confere isso.
</PareEPense>

## Repetir na sua máquina

O caminho CPU é o padrão. O extra `modelo` instala o PyTorch sem CUDA; o extra `gpu` instala a versão para NVIDIA. Você escolhe um deles nas instruções do coletor, no último trecho da IDE e no README do projeto. Os dois alimentam o mesmo medidor, mas usam ambientes e precisões distintos. Compare lotes dentro de cada ambiente antes de atribuir uma diferença ao dispositivo.

O nosso coletor chama o modelo diretamente. Não manda requisições concorrentes para uma API e adivinha o tamanho do lote: os lotes são os tensores de entrada que ele constrói. Uma API fechada exigiria outras evidências para identificar o mecanismo interno.

<PareEPense pergunta="A sua máquina devolveu uma sequência diferente da gravação, mas repetiu essa nova sequência em todas as tentativas. Isso contradiz a medida?">
Não. A referência da sua coleta é a primeira execução dela. Compare dentro do mesmo ambiente; mudar biblioteca, precisão ou dispositivo pode mudar a sequência sem causar variação entre repetições dessa coleta.
</PareEPense>

## O que esta medida não resolve

O percentual abaixo conta sequências iguais à referência; não conta respostas certas. Mesmo quando a amostra inteira repete, a conclusão é sobre as condições registradas. Não é uma garantia para qualquer servidor, nem prova de que o conteúdo está correto.

Uma das respostas de referência termina em “compromet”, porque o limite de 48 tokens cortou a continuação. Ela repetiu assim nas dez tentativas de cada lote. O comparador preserva esse resultado; não confunde uma sequência idêntica com uma resposta completa.

A comparação com kernels invariantes ao lote é uma extensão para a outra máquina com GPU. O [vLLM oferece esse modo com requisitos de hardware e limitações de versão](https://docs.vllm.ai/en/latest/features/batch_invariance/). Ela ainda não foi medida aqui. Não precisamos preencher essa lacuna com um gráfico inventado: a coleta CPU já é uma observação que você consegue conferir.
